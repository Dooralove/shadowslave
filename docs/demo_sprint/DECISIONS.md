## 1. Принятые решения

### D-01. Демо — пост-Кошмарная цепочка

**Решение:** основной демонстрационный маршрут — `main_menu → police_precinct → academy_approach → academy_gate → academy_campus → academy_sleeper_center → black_sea_platform → tide_descent → labyrinth_first_fragment → post_nightmare_finale`.

**Причина:** решение пользователя; это единственный маршрут, который одновременно использует новый контент (академия, статуя, Лабиринт) и может быть доведён до законченного конца.

**Следствие:** отчёты 03 и UI/UX, писавшиеся под Первый Кошмар/Лабиринт, переранжируются, но их факты не отменяются. Первый Кошмар остаётся доступной второй аркой.

### D-02. Полный сюжет — программа, а не один спринт

**Решение:** «весь сюжет, все локации, все модели» разбивается на M0–M7:

- M0 — foundation/audit;
- M1 — пост-Кошмарная цепочка;
- M2 — академия;
- M3 — Лабиринт;
- M4 — Первый Кошмар;
- M5 — Acts C–D;
- M6 — западный город;
- M7 — релиз.

**Причина:** полный сюжет до глав 100 — это 50+ сцен, 20+ персонажей, 15+ монстров и месяцы работы. Обещать это за 3 часа — ложь.

### D-03. Модели — Hyper3D web UI + Blender cleanup

**Решение:** основной конвейер — генерация в Hyper3D web UI по готовым промптам, затем retopo/UV/tangents/rig/weights/LOD/PBR в Blender и импорт в Godot.

**Причина:** выбор пользователя; API Creator недоступен, web UI доступен.

**Следствие:** ни одна модель не считается финальной без pipeline-чеклиста. Текущие GLB — fallback.

### D-04. Следующий milestone — M2 «Академия»

**Решение:** после M1 делать M2: участок, Джет, Джулиус, индукция, капсулы, Hollow, затем M3.

**Причина:** выбор пользователя; это прямой сюжетный шаг к Чёрному морю и Лабиринту.

### D-05. Один demo flow, три уровня fallback

**Решение:** DEMO_FLOW имеет уровни A (полный), B (до Чёрного моря), C (Первый Кошмар).

**Причина:** демо не должно зависеть от нестабильного Лабиринта. Лучше честный B, чем A с застреванием.

### D-06. Один Quest Framework

**Решение:** использовать существующий `QuestSystem`; второй framework не создавать.

**Причина:** 7 квестов, каталог, цели, награды, журнал, snapshot и SaveSystem уже есть.

### D-07. Инвентарь и Памяти — demo-only до P1

**Решение:** `InventoryPrototype`/`RpgDemoSession` остаются витриной; не выдавать их за канонический инвентарь. Реальный инвентарь/Памяти — P1/P2.

**Причина:** нет каталога предметов, слотов, иконок и связи с state.

### D-08. Разделение HUD/quest слоёв

**Решение:**

- пост-Кошмарные сцены — `GreyboxLocation` + `GameplayHud` + `CampaignGuide.set_external_objective`;
- Лабиринт — `LabyrinthQuestDirector` + `QuestSystem` + `GameplayHud`;
- S00–S15 — `CampaignGuide`/`BeatDirector`, без активации QuestSystem scope.

**Причина:** один HUD, один journal, без конкурирующих целей.

### D-09. N07/N18/N25 приняты

**Решение:** N07 Bloodbane, N18 личинка Шифти, N25 две личинки считаются исправленными по коду и целевым тестам.

**Ограничение:** живой бой N18 и ручной проход — **NOT TESTED**; в `fast_mode` бой пропускается.

### D-10. `project.godot` — только TD

**Решение:** `[rendering]` восстановлен; autoloads `PauseMenuSystem`, `QuestSystem`, `SaveSystem` утверждены; `MCPRuntime` — временный и удаляется из релиза.

**Причина:** параллельные правки уже удаляли P5-настройки.

### D-11. Placeholders разрешены, но маркируются

**Решение:** на время демо допустимы `Mannequin`-плейсхолдеры для Джет, Джулиуса, медика, охраны, Нефис, Кассии, Тео.

**Условие:** в отчёте и UI не называть их финальными моделями.

### D-12. Никакой массовой реализации до утверждения основы

**Решение:** сначала `MASTER_AUDIT.md`, `BACKLOG.md`, `DEMO_FLOW.md`, `DECISIONS.md`; затем P0.

**Причина:** 10 чатов уже создали 574 записи в рабочем дереве; без консолидации получится 11 несовместимых наборов.

### D-13. Приёмка демо невозможна без build и ручного прохода

**Решение:** PASS только при: import exit 0, полный GUT 0 fail, export build запускается, ручной проход DEMO_FLOW записан.

**Причина:** headless-тесты не заменяют игру.

### D-14. Документация — не доказательство

**Решение:** все числа и статусы в README/DECISIONS/route verification считаются устаревшими, пока не сверены с кодом и прогоном.

### D-15. MCP — инструмент доказательства, не зависимости

**Решение:** после restart Godot MCP не подключён; до подключения использовать headless GUT и read-only capture-скрипты.

### D-16. Геометрия Лабиринта G1–G5 — P0

**Решение:** Z04, Z11, Z08→Z09, Z05→Z06, Z03→Z05 исправляются до демо. «Проходимо по дизайну» не считается.

### D-17. Прилив 120 с — демо-компрессия

**Решение:** в демо используется 120-секундный цикл; 16-минутный цикл, утопление и штормовой сценарий — P1.

**Причина:** 16 минут ожидания несовместимы с 45–70-минутным демо.

### D-18. 7 квестов — каркас, SQ-FS — M3

**Решение:** 7 существующих квестов обязательны для M3; SQ-FS-01…05 — P1/P2, не в S00–S15.

### D-19. `coral_labyrinth` — sandbox

**Решение:** старый `coral_labyrinth` остаётся sandbox; демо-Лабиринт — `labyrinth_first_fragment`.

### D-20. Экспорт — P0

**Решение:** `export_presets.cfg` и Windows build создаются до демонстрации. Без build демо не принимается.

### D-21. Один слот сохранения — достаточно для демо

**Решение:** `SaveSystem` с одним слотом; слоты/список/миграции — P2.

### D-22. Пост-Кошмар — вертикальный срез, не вся глава

**Решение:** M1/M2 — срез с NPC, диалогами, целями и финалом; полная академия/Hollow — P1.

### D-23. Отчёты 03/UI не переписываются

**Решение:** их факты сохраняются; приоритеты переранжируются под DEMO_FLOW. Противоречие «S00–S15 vs Лабиринт» закрыто D-01.

### D-24. Граница «всех моделей»

**Решение:** «все модели» = все модели для документированного текущего сюжета (Первый Кошмар, пост-Кошмар, Forgotten Shore, Acts C–D, западный город). Вся веб-новелла за пределами этих документов в объём не входит.

### D-25. Модель без pipeline не интегрируется

**Решение:** обязательны retopo, UV, tangents, rig/weights, LOD0/1/2, PBR, лицензия, Godot-проверка.

### D-26. Цель производительности

**Решение:** 1080p, ≥60 FPS на RTX 3060 Laptop, draw calls <1500, VRAM <4 GB. В бою и на всех зонах — **NOT TESTED**.

### D-27. Git

**Решение:** без отдельного указания пользователя не коммитить, не push, не переключать ветку, не чистить дерево. Все изменения — в рабочем дереве.

### D-28. M1 и tech demo — два разных acceptance-объёма

**Решение:** M1 — обязательный вертикальный срез `main_menu → … → labyrinth_first_fragment Z01–Z10`, финал в лагере Z10, 18–25 минут. Tech demo — полный фрагмент Z01–Z18 с `post_nightmare_finale`, 50–70 минут. M1 принимается первым; tech demo не блокирует M1, но требует отдельного ручного прохода.

**Причина:** `narrative_design.md` и `level_implementation_plan.md` определяют M1 как Z10; `DEMO_FLOW.md` ранее описывал только полный Z18. Это расхождение исправлено, а не замаскировано.

**Следствие:** `DEMO_FLOW.md` содержит оба режима; `DemoEndZone` в Z10 работает при `demo_mode_m1` (default) и не при `demo_mode_full`; `FinalZone` Z18 — только при `demo_mode_full`.

### D-29. Канонические ID и legacy aliases

**Решение:** design package использует канонические ID из `INTEGRATION_CONTRACTS.md`. Для уже написанного кода допускаются legacy aliases на время миграции: `jet` → `jett`, `precinct_mirror_seen` → `p05_mirror_seen`, `academy_jet_seen` → `jett_advice_heard`, `academy_gate_checked` → `academy_gate_passed`, `sleeper_ready` → `capsule_entered`, `black_sea_stars_seen`/`black_sea_sword_seen` → `statue_seen`, `demo_m1_completed` → `post_nightmare_demo_completed`, `demo_completed` → `post_nightmare_completed` (tech demo). Aliases не создают второй state-системы и удаляются после миграции.

**Причина:** текущий код и design-документы используют разные имена; без contract'а интеграция снова разойдётся.

**Следствие:** новые сцены, диалоги и тесты используют только канонические ID; legacy aliases читаются, но не пишутся.

### D-30. Design Package lock

**Решение:** `MASTER_PLAN.md`, `FILE_OWNERSHIP.md`, `AGENT_TASKS.md`, `INTEGRATION_CONTRACTS.md` — обязательные документы Stage 3. Изменение общих интерфейсов, ID или владения файлами — только через новую версию Design Package и запись в этом файле.

**Причина:** 10 чатов работают в одном дереве; без lock'а снова появятся параллельные реализации одного и того же.
